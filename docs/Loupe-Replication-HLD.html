FARE's architecture on SEC EDGAR filings

We rebuild the base paper's multi-agent system from its text, run it on SEC filings for our 25 companies, measure every stage, and make each stage swappable so a React playground can compare variants side by side. The same pipeline later carries over to Indian filings.

1 · Goals and scope

Four research questions for this phase

Each has a measurable answer, and together they form the first results chapter of the report.

RQ1

Transfer. When FARE is rebuilt from the paper and run on SEC filings instead of transcripts, do its conclusions still hold? For example: the same model ranking per agent, and the same speed ranking.

RQ2

Multi-agent value. Does routing to specialised agents beat a single-agent RAG system on the same questions? FARE asserts this but never measures it.

RQ3

Judge reliability. FARE's judges were never checked against people. How often does each judge version agree with human grades?

RQ4

Which stage matters. Swapping one stage at a time (chunking, embeddings, retrieval, routing, prompts, model), which changes move the scores, and at what cost?

IN SCOPE
  • FARE's orchestrator and six agents, rebuilt from the paper
  • SEC EDGAR filings by CIK for our 25 companies
  • Several variants per stage, chosen by config
  • Versioned judges and per-stage metrics
  • FastAPI backend and React benchmarking playground
NOT IN THIS PHASE
  • Earnings-call transcripts and FARE's original dataset
  • Investment advice of any kind
  • Indian filings, LODR taxonomy, personas, chat product (Phase I)
  • Fine-tuning models

3 · From paper to code

Rebuilding FARE when the paper is all we have

Without FARE's code, prompts or data, we rebuild the method from its description and test whether its conclusions hold on new data. Six steps, each producing a file the report can cite.

STEP 1 · EXTRACT

Every design element with its page and a status of Specified, Partly specified or Not specified. Drafted

docs/fare/01-extraction-sheet.md

STEP 2 · REGISTER THE CLAIMS

Every reported result as a hypothesis, with the paper's numbers. Drafted

docs/fare/02-claims.md

STEP 3 · FILL THE GAPS, ON THE RECORD

For every item not fully specified: options, choice, reason, and whether it could change results. If it could, it becomes an ablation.

docs/fare/03-decisions.md

STEP 4 · REBUILD THE PROMPTS

Written from the agent descriptions, versioned, labelled as reconstructions.

configs/prompts/fare/*.yaml

STEP 5 · BUILD, THEN CHECK CONFORMANCE

A teammate who did not write the code checks every Specified item against the running system.

docs/fare/05-conformance.md

STEP 6 · TEST THE CLAIMS

Each claim marked holds, partly or does not hold, with confidence intervals, plus a table of every deviation from the paper.

Replication chapter of the report

5 · System architecture

A pipeline of swappable stages, behind an API

Every stage is picked from a registry by the pipeline config. The playground and the evaluation harness both call the same API.

flowchart LR
  subgraph ING["Ingest and index"]
    ED["EDGAR filings by CIK"] --> PR["Parse"] --> CK["Chunk"] --> EM["Embed"] --> IX[("Index + metadata")]
  end
  subgraph AG["Agent layer (LangGraph)"]
    OR{"Orchestrator"}
    OR --> A1["Statement Extraction"]
    OR --> A2["Tone + critic"]
    OR --> A3["Tone Shift"]
    OR --> A4["Comparison"]
    OR --> A5["Thesis Check"]
    OR --> A6["Scenario"]
  end
  Q["Query"] --> OR
  RT["Retrieve"]
  IX --> RT
  AG <--> RT
  AG <--> MG["Model gateway"]
  TL["Tools: XBRL, prices, calculator"] <--> AG
  AG --> ANS["Answer + citations"]
  ANS --> JD["Judges (versioned)"]
  JD --> ST[("Results + traces")]
  ST --> API["FastAPI"]
  API --> UI["React playground"]

One query enters the orchestrator, which activates one agent. Judges score the answer after the fact; they never influence the answer (except the Tone critic, see decisions log).

6 · Components

Each component has its own metric

C1

EDGAR source

Does
Lists and downloads 10-K, 10-Q and 8-K filings (with exhibits) for each CIK. Caches raw files by accession number.
Design
SEC submissions API; declared User-Agent; at most 10 requests per second. NseSource joins in Phase I.
Measured by
Coverage: filings fetched vs filings listed for the universe.
C2

Parse, chunk, embed, retrieve

Does
Turns filings into sections and chunks with metadata, embeds them and retrieves the top-k for a query, filtered by company and period.
Design
Four registries, v0 = FARE's settings. Variants in section 7.
Measured by
Section-boundary accuracy; Recall@k, MRR, nDCG@10; RAGAS context precision; wrong-period rate.
C3

Model gateway

Does
The only path to an LLM. Picks provider and model from config, returns text or schema-checked JSON.
Design
LiteLLM underneath; disk cache keyed by model, prompt hash and parameters; logs tokens, latency and cost; temperature 0.
Measured by
Supplies cost and latency to every result.
C4

Orchestrator and agents

Does
Routes each query to one of six agents; the agent retrieves, reads chunks in batches and answers with citations.
Design
LangGraph graph with a shared state. Routing and agent prompts are versioned configs. Tools (XBRL lookup, price returns, calculator) are typed functions; the Scenario agent uses price returns from v0.
Measured by
Routing accuracy on labelled queries; per-agent FARE metrics; steps, failures, cost.
C5

Judges and evaluation harness

Does
Runs a pipeline config over a query set, scores each answer with the chosen judge version, writes result rows.
Design
Judge versions are plugins like any stage. Dev/test splits frozen and tagged; the harness refuses test runs without a flag.
Measured by
Judge agreement with human grades (Cohen's κ).
C6

Results store and API

Does
Keeps every run, trace and score; serves them to the playground; runs live pipelines on request.
Design
DuckDB tables + JSONL traces; FastAPI with POST /runs, GET /runs/{id}, GET /variants, GET /benchmarks.
Measured by
Any past result can be regenerated from its config hash.

8 · Evaluation

How we know a change is an improvement

Versioned judges. A new judge version changes the measuring tool, not the system. Compare system versions only under the same judge version. Compare judge versions by how often they agree with human grades, not by which gives higher scores.

13 · Risks

What could derail the phase

RiskMitigation
The paper leaves out prompts, judge model and batch sizeDecisions log with reasons; ablate any gap that could change results; email the authors.
Filings differ from transcripts (no dialogue, longer, legal wording)That difference is RQ1's subject; report per-agent where claims break.
Too many variant combinations to affordOne stage at a time; response cache; 50-query dev slices; full runs only at gates.
Google Search results drift, so judge v1 is not repeatableStore every retrieved reference with the run; judge v2 freezes references.
Gemini 2.5 models retired by the providerCheck availability in M0; record the substitute as a deviation.
React playground eats agent-building timeOne owner (stream D); the UI only reads the API; tracer UI first, polish at M3.
SEC rate limitsUser-Agent, throttle, local cache of every filing.
