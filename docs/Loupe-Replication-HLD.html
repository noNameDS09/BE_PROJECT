1 · Goals and scope

Four research questions for this phase

Replication is a research result in its own right. Each question has a measurable answer, and together they form the first results chapter of the report.

RQ1

Reproduction. When FARE is rebuilt from the paper alone, do its main claims still hold? For example: the same model ranking, and the agent workflow beating simpler baselines.

RQ2

Transfer. Does FARE's architecture hold up when moved from earnings-call transcripts to SEC filings (10-K, 10-Q, 8-K)? Does it beat a plain RAG baseline there?

RQ3

Judge reliability. FARE relies on LLM-as-a-judge without human validation. How well does the judge agree with human graders on our data?

RQ4

Error attribution. When an answer is wrong, is it a retrieval failure, a reasoning failure or an arithmetic failure? What does each model cost per correct answer?

IN SCOPE
  • FARE's agent graph, rebuilt from the paper
  • SEC EDGAR ingestion by CIK: 10-K, 10-Q, 8-K, XBRL facts
  • Model-agnostic runs across several LLMs
  • Evaluation harness with metrics for every component
  • Ablations against simpler baselines
NOT IN THIS PHASE
  • Indian filings, LODR taxonomy, NSE ingestion (Phase I)
  • Chat UI, personas, charts, exports
  • Fine-tuning any model
  • Production concerns: auth, multi-user, deployment

3 · From paper to code

Rebuilding FARE when the paper is all we have

Without FARE's code, prompts or data, we cannot rerun the authors' experiment. We rebuild the method from its description and test whether its claims hold on new data. This is called a conceptual replication, and it is a recognised type of study. Six steps, each producing a file the report can cite.

STEP 1 · READ AND EXTRACT

Everyone reads the paper. One person fills the extraction sheet: every design element (agents, prompts, retrieval settings, models, dataset, metrics) with its page or section and a status of Specified, Partly specified or Not specified.

docs/fare/01-extraction-sheet.md

STEP 2 · REGISTER THE CLAIMS

List every result the paper reports, with its number and table or figure. For example, "Qwen2.5-7B-Instruct gives the strongest reasoning". Each claim becomes a hypothesis we test.

docs/fare/02-claims.md

STEP 3 · FILL THE GAPS, ON THE RECORD

For every item that is not fully specified, write a short decision: the options, the choice, the reason, and whether it could change results. If it could, it becomes an ablation. Default rule: pick the simplest option that fits the paper's text, using the defaults of the libraries FARE names.

docs/fare/03-decisions.md

STEP 4 · REBUILD THE PROMPTS

Copy any prompts printed in the paper word for word. Otherwise write them from the agent role descriptions, version them, and label them as reconstructions.

configs/fare/prompts/*.yaml

STEP 5 · BUILD, THEN CHECK CONFORMANCE

Implement the graph from the extraction sheet. A teammate who did not write the code then checks every Specified item against the running system and signs it off.

docs/fare/05-conformance.md

STEP 6 · TEST THE CLAIMS, REPORT DEVIATIONS

Run the claims on substitute transcript data (track R-A) and SEC filings (track R-B). Report each claim as holds, holds partly, or does not hold, with confidence intervals, plus a table of every deviation from the paper.

Replication chapter of the report

WHAT SUCCESS MEANS HERE
  • Every Specified item is implemented and signed off.
  • Every gap has a written, justified decision.
  • Every claim is tested with confidence intervals.
  • Matching FARE's exact numbers is not the goal. Different data and prompts make that impossible. Matching its conclusions is the goal.
IF A CLAIM DOES NOT HOLD
  • That is a finding, not a failure. Report it.
  • Check the decisions log first: rerun the ablation for any gap that could explain the difference.
  • A claim that fails on SEC filings but holds on transcripts is itself a result about transfer (RQ2).
4 · Two replication tracks

Reproduce first, then transfer

EDGAR does not host earnings-call transcripts systematically, so "FARE on SEC filings" means two things. Keep them separate so each result is interpretable.

TRACK R-A · CLAIM CHECK

FARE's task, substitute data

Run the rebuilt system on a public earnings-call transcript dataset with FARE's two named models. Candidates: ECTSum and SubjECTive-QA (check licences). Test whether FARE's conclusions hold, not whether we hit its exact numbers.

Answers RQ1. Keeps the comparison on FARE's own document type, so any difference comes from our rebuild rather than from the switch to filings.

TRACK R-B · TRANSFER

FARE's architecture, SEC filings by CIK

Same graph and models, pointed at 10-K, 10-Q and 8-K filings. Earnings press releases (8-K Item 2.02, Exhibit 99.1) are the closest filing to a transcript.

Answers RQ2 to RQ4. This is also the dry run for Indian filings, which are also regulator-mandated documents.

Company universe for R-B: use the companies covered by the public evaluation sets in section 7 (FinanceBench's open sample, FinDER), so their human-written evidence labels apply directly. Pin fiscal years FY2022 to FY2025.

6 · Components

Nine components, each with its own metric

"Measured by" is the key column: if a component cannot be scored on its own, we cannot tell whether a change improved it.

C1

Source adapters

Does
Lists and downloads filings for a CIK, form type and date range. Stores raw files once, keyed by accession number and content hash.
Design
One FilingSource interface. EdgarSource now, NseSource in Phase I. Respects SEC fair access: a declared User-Agent and at most 10 requests per second.
Measured by
Coverage: filings fetched vs filings listed in the EDGAR index for the universe.
C2

Parser

Does
Turns HTML filings and PDF transcripts into clean text with structure: 10-K items (1A Risk Factors, 7 MD&A…), page or character offsets, and tables kept separately.
Design
HTML parser for EDGAR, PyMuPDF for PDFs (FARE's choice, and needed for NSE later). Output is a Document (section 8).
Measured by
Section-boundary accuracy on 30 hand-checked filings; share of evidence strings from the eval sets found verbatim in parsed text.
C3

Chunker and index

Does
Splits documents into chunks, embeds them and builds a FAISS index. Stores metadata (CIK, form, fiscal period, section) for filtering.
Design
FARE's settings as the default config. Section-aware chunking, BM25 hybrid search and a reranker are separate ablation switches. Metadata filters matter in finance: most wrong answers cite the wrong year.
Measured by
Recall@k, MRR and nDCG@10 against the gold evidence in the eval sets; index build time and memory.
C4

Model gateway

Does
The only way any component calls an LLM. Chooses the provider and model from config and returns text or schema-validated JSON.
Design
Wraps a multi-provider client (LiteLLM). Caches every response on disk, keyed by model, prompt hash and parameters, so reruns are free and reproducible. Logs tokens, latency and cost per call. Temperature 0 by default.
Measured by
Not scored itself. It supplies the cost and latency columns for every other result.
C5

Agent graph

Does
Implements FARE's six-agent workflow in LangGraph, with a shared state object and a step limit.
Design
The graph is defined in config (nodes, edges, prompts), so the real FARE roles drop in once the paper is read. Working hypothesis until then: Planner → Retriever → Financial analyst and Narrative analyst → Synthesizer → Evaluator, which can send the answer back for revision.
Measured by
Trajectory metrics: correct tool calls, steps per answer, revision loops, failures and timeouts.
C6

Tools

Does
Functions the agents may call: retrieve chunks, fetch a filing section, look up an XBRL fact, run a calculation.
Design
Replica mode enables only the tools FARE has. Extension mode adds XBRL lookup and a deterministic calculator; this is our first contribution and the preview of Loupe's compute stage. Each tool has typed inputs and outputs and unit tests.
Measured by
Unit tests; numeric accuracy against XBRL facts (eval set E4).
C7

Evaluation harness

Does
Loads a versioned dataset, runs a named system config over it, scores each layer and writes a results report.
Design
Our own runner, so every metric is transparent in the report. Library metrics (for example Ragas faithfulness) only as a cross-check. Detail in section 7.
Measured by
Judge-vs-human agreement (RQ3) is the harness's own quality check.
C8

Trace and experiment store

Does
Keeps every run: config snapshot, git commit, dataset version, per-question outputs, full agent trace, cost.
Design
JSONL traces plus a DuckDB results table, all local. Optional LangSmith tracing, which plugs into LangGraph directly.
Measured by
Any past result can be regenerated from its run id.
C9

Interfaces

Does
A command line for everything: ingest, index, ask, eval, compare runs.
Design
For example loupe eval run --config fare_replica.yaml --dataset E1-dev. A notebook or small Streamlit page to browse traces comes later. No chat UI in this phase.
Measured by
Not scored.
7 · Evaluation design

How we will know we are improving

Every change runs against a frozen dev set and is compared with the best previous run. The test set is touched only at milestones.

Evaluation datasets

IdDatasetWhat it testsSource
E1FinanceBench, open sampleQA over 10-K / 10-Q / 8-K with human evidence passages and pages. Retrieval and answer quality.Public (Islam et al., 2023). Check licence.
E2FinDERAnalyst-style queries over 10-K with evidence. Retrieval under vague queries.Public (2025). Check access.
E3Loupe-SEC goldAbout 200 questions written by the team with evidence spans. Question types mirror Phase I: risk, events, numbers, comparisons.Ours. Two authors per item.
E4XBRL numeric setQuestions generated from XBRL company facts ("FY2024 revenue", "debt-to-equity"). Exact ground truth, hundreds of items for free.Ours, generated from SEC data
E5Public transcript setStand-in for FARE's unavailable data. Track R-A claim check.ECTSum or SubjECTive-QA. Check licence.

Split each set once into dev (tuning) and test (reporting), stratified by company and question type, and freeze the split with a version tag.

Baseline and ablation ladder

IdSystemQuestion it answers
B0LLM only, no retrievalHow much does the model already know?
B1Plain RAG: retrieve once, answer onceThe standard baseline every reviewer expects
B2FARE replica (strict)RQ1 and RQ2
B3B2 + XBRL lookup and calculatorDoes deterministic compute remove numeric errors?
B4B3 + citation check and calibrated judgeDoes grounding raise faithfulness?

Run each rung with 3 to 4 models. Start with FARE's two (Qwen2.5-7B-Instruct via a hosted API, Gemini 2.5 Flash-Lite) and add one or two others. That makes a model × system grid, and the cost column shows which trade-offs are worth it.

JUDGE PROTOCOL
  • The judge comes from a different model family than the model being judged.
  • A fixed written rubric, versioned with the dataset.
  • Two team members grade a 100-item subset by hand. Report κ between them and between humans and the judge.
  • This directly addresses FARE's stated limitation.
STATISTICAL RIGOUR
  • Temperature 0. Where a model is non-deterministic, 3 runs.
  • 95% bootstrap confidence intervals on every headline number.
  • Paired tests when comparing two systems on the same questions.
  • Ticker-trap control (Paper 8): rerun a subset with company names masked.
flowchart LR
  C["Change: prompt, chunking, model or graph"] --> D["Run dev suite"]
  D --> M["Metrics per layer"]
  M --> Q{"Better than last best?"}
  Q -- yes --> K["Keep and log run id"]
  Q -- no --> X["Read traces, revert or fix"]
  K --> T["Test set at milestones only"]

The improvement loop. A change is kept only if the dev metrics for the layer it touched improve without regressing the others.

8 · Data contracts

The objects passed between layers

Agree on these before splitting work. With fixed contracts, four people can build four layers in parallel.

# Document — output of C2
doc_id, source ("edgar" | "transcripts" | "nse"), cik, company, form ("10-K"…), accession,
fiscal_year, fiscal_period, filed_at, url, sections: [{name, start_char, end_char}], text, tables[]

# Chunk — output of C3; every citation points to one
chunk_id, doc_id, section, start_char, end_char, text, embedding_model, index_version

# Query — one eval item or user question
query_id, question, cik?, fiscal_period?, dataset, split, gold: {answer, evidence: [{doc_id, span}]}

# Answer — output of C5
answer_text, claims: [{text, chunk_ids[]}], numeric_values: [{value, unit, source}], confidence

# Trace — written by C5, stored by C8
run_id, query_id, steps: [{agent, tool?, input, output, model, tokens, latency_ms, cost}]

# EvalRecord — output of C7
run_id, query_id, config_hash, dataset_version, metrics: {recall@k, correct, faithful, …}, judge: {model, verdict, reason}
9 · Technology choices

Chosen to fit an 8 GB M1 laptop

LLMs run on hosted APIs. Everything else runs locally on CPU or Apple's GPU.

ConcernChoiceWhy
Language, environmentPython 3.12 with uvThe machine has 3.14; FAISS and PyTorch wheels are safest on 3.12.
OrchestrationLangGraphSame as FARE, required for a fair replication.
LLM accessLiteLLM behind our gatewayOne interface for Gemini, Claude, OpenAI-compatible hosts serving Qwen, and others. Switching models is a config change.
EmbeddingsSentenceTransformersSame as FARE. Use FARE's model if it fits in memory, otherwise a small model as a documented deviation.
Vector indexFAISS (faiss-cpu)Same as FARE. A flat index is fast enough for the replication corpus.
EDGAR accessSEC submissions and XBRL APIs, plus an HTML parserOfficial, free, tested today: Apple's filings list and XBRL facts downloaded.
PDF parsingPyMuPDFSame as FARE; needed for NSE PDFs later.
Results and tracesDuckDB + JSONL, optional LangSmithNothing to run as a server; results are queryable with SQL.
Qualitypytest, ruff, pre-commitTool unit tests and parser tests run on every commit.

12 · Risks

What could derail the replication

RiskMitigation
The paper leaves out details (prompts, agent roles, settings)Decisions log with reasons; ablate any gap that could change results; email the authors.
FARE's code, prompts and data are unavailableConceptual replication (section 3): test claims, not exact numbers; substitute transcript data for R-A; every gap logged as a decision.
API cost across many models and runsResponse cache; develop on a 50-item dev slice; full runs only at gates; set a budget per model.
8 GB RAM limits embedding models and indexesSmall embedding model, flat FAISS index, batch encoding; document deviations from FARE.
LLM judge is biased or lenientCross-family judge, fixed rubric, human-graded subset with κ.
Tuning on the test set by accidentFrozen splits with version tags; the harness refuses test runs unless a flag is set.
SEC rate limitingDeclared User-Agent, request throttle, local cache of every raw filing.
