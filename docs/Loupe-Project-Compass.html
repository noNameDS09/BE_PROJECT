SPPU BE Project · AI & Data Science · Status as of 29 Sep 2026

Loupe

Loupe is a chat copilot that answers questions about Indian listed companies from their SEBI-mandated disclosures. Every answer cites the filing it came from, and every number comes from deterministic code, never from the language model.

2 · What we build

Four stages. Each stage borrows a proven method and applies it to Indian filings.

An analyst asks a question in chat. The agent runs the stages it needs and answers with citations. Stages 1 to 3 also run in batch to keep the event store fresh.

STAGE 1

Retrieve

Does
Pulls announcements, results and shareholding filings per company; extracts PDF text; keeps source URL, date and page.
Sources
NSE / BSE corporate announcements, NEAPS XBRL, rating-agency releases
Out
Document store with provenance
STAGE 2

Extract

Does
Tags each filing with event types from the LODR taxonomy. Every tag must quote the filing verbatim. A second pass scores each quote 1 to 5.
Method
Dolphin et al., Papers 1 & 2
Out
Events table: company, type, quote, page, score
STAGE 3

Compute

Does
Python functions compute pledge %, RPT ratios, results ratios and the distress score from XBRL and the events table.
Method
Tool-using copilot pattern, Paper 7
Out
Numbers with the inputs they came from
STAGE 4

Talk

Does
A LangGraph agent plans, calls the retrieval, event and compute tools, and writes an answer where each claim links to a quote.
Method
FARE (base paper), plus personas
Out
Cited answer, chart, or short memo

How this maps to the architecture diagrams. The Search Engine is Stage 1. The Risk Engine is Stages 2 and 3. The Query Engine is Stage 4. The diagrams list about 16 agents; for the build, treat most of them as plain functions (tools) and keep only one planning agent plus a persona prompt layer. That is simpler to debug and still meets the "agent-orchestrated" claim.

Why the base paper fits. FARE is a LangGraph multi-agent system with RAG over earnings-call transcripts. Its own stated limitations are "no formal risk framework" and "reliance on LLM-as-a-judge without human validation". Our taxonomy, deterministic compute and hand-annotated gold set answer exactly those gaps. Use that as the novelty argument.

The proposal PDF and the August review deck both say "Ingestion: standard public filings SEC 10-K". The India pivot exists only in PROJECT-BRIEF.md v0.2. If the guide approved the SEC version, the change needs explicit sign-off.

Fix: get written confirmation from the guide this week. Then update the title-page scope line and slide 4.

Medium

"LLM-as-judge raises precision from 12% to 96%" misstates Paper 2

Paper 2 reports precision by quality-score bin: 12% for tags scored 1, 96% for tags scored 5. Keeping only score 5 retains 34% of tags. The actual finding is that scoring in a separate second pass gives a calibrated score, while inline self-scoring does not. The architecture pages repeat this as "96% precision gate".

Fix: reword in the proposal, deck and diagrams. Replicating this calibration curve on Indian filings is a good result to report.

Medium

The scope is too wide for four people and one academic year

The brief has 14 features, 8 personas, about 16 agents, 6+ data sources and the full NSE 200 universe. DRHP teardown alone (500 to 900 pages per document) is a project by itself.

Fix: commit to the MVP in section 5. Keep the full matrix in the report as future scope.

Medium

Data access has not been checked

NSE's website blocks automated clients aggressively, and the MCA portal uses CAPTCHAs and paid downloads. Neither problem shows up in the plan.

Fix: in week 1, prove you can fetch one quarter of announcements and one XBRL file for 5 companies, within each site's terms and at a low request rate. Drop MCA from the MVP.

Low

Strong claims need sources

"World-first", "10 of 14 globally unique" and "verified Aug 2026" will draw questions. The architecture pages also show the SEC "119-category taxonomy", which belongs to Paper 2, not to this project.

Fix: soften to "to our knowledge, no published system…" and cite what was searched. Show our own taxonomy count (47 event types in draft v0).

6 · Decisions the team needs to make

Six open questions, each with a recommendation

These come from the brief's open questions, plus the ones the build forces. Expand one to see the reasoning.

Is the India pivot approved by the guide?Confirm this week

Every later choice depends on it. If the guide prefers SEC data, the same pipeline works on 8-K filings, and Papers 1 & 2 become direct baselines. The India version is more novel but riskier on data access.

Which orchestration framework?LangGraph

FARE uses LangGraph. Using the same framework lets you run a FARE-style baseline and compare fairly. It also gives explicit state graphs that are easy to draw in the report.

Which LLMs?Open 7B model + API judge

Run bulk extraction with an open instruction-tuned model such as Qwen2.5-7B-Instruct (FARE's best reasoner) on a local GPU or cheap host. Use a stronger API model only for the second-pass scoring and evaluation, which is the pattern Paper 2 uses. Set a monthly budget early.

How to store the "evidence graph"?Postgres + pgvector

Documents, chunks, events and claims are four relational tables linked by foreign keys, which is a graph in practice. pgvector handles retrieval in the same database. Add a graph database only if a query really needs one.

What chat front end?Chainlit or Streamlit

Both show tool steps and citations with little code. A custom React front end costs weeks and adds nothing to the evaluation.

Build order?Extraction first, thin chat early

Build extraction and compute first, because the research result lives there. Stand up a thin chat that calls one real tool by the end of phase 1, so the demo path is never blocked and integration problems show up early.

8 · Evaluation

What to measure, and what to compare against

The brief's four evaluation areas, turned into concrete metrics. Baselines: (a) plain RAG over the same documents, (b) a FARE-style agent without our compute tools or taxonomy.

StageMetricGround truth
ExtractPrecision, recall and F1 per event type; share of quotes found verbatim; precision by quality-score binGold set of about 300 announcements; inter-annotator agreement (Cohen's κ)
ComputeExact-match rate of pledge %, RPT ratio and results ratiosHand calculation from XBRL, 50 company-quarters
TalkCitation precision (claim supported by cited quote); numeric hallucination rate; answer correctness100 scripted questions, human-graded, compared with both baselines
DistressDoes the score rise before downgrades and defaults? AUC over a 90-day lead windowRating actions and defaults found in the filings themselves
UsersTask time, perceived trust, errors found3–5 analyst sessions, if contacts exist

Paper 8's warning applies: test on companies and quarters the prompts were not tuned on, so the system is not just recognising familiar tickers.
